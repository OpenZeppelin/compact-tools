# compact-deployer invariants

What the fragmented-deploy path must always hold. The `// INV-N` tags in `src/`
point here.

"Enforced in" is the code that makes the statement true. "Pinned by" is the test
that fails if it stops being true. Numbering is stable: an invariant is never
renumbered, only restated.

## Type-level

TypeScript types and pure functions. Breaking one fails to compile.

| INV | Statement | Enforced in | Pinned by | Severity |
|---|---|---|---|---|
| INV-1 | `planFragments` returns fragments that are pairwise disjoint, jointly equal to the input circuit set, each non-empty, indexed `0..n-1` in order. Fragment 0 is non-empty whenever the input is. | `services/deploy-plan.ts` | `deploy-plan.test.ts` "partitions the input across fragments" | High |
| INV-2 | The same `(circuits, budget)` yields the same plan. Circuits are sorted by a locale-independent code-unit comparator before splitting, and fragment 0 is the first `budget` names. No clock, randomness, or environment input. | `services/deploy-plan.ts` `sortCircuits` | `deploy-plan.test.ts` "ignores input order and repeats identically", "puts the first sorted names in fragment 0" | Medium |
| INV-3 | `DeploymentRecord` is a discriminated union on `status` with exactly `pending`, `partial`, `confirmed`. `checkRecordable` ends on `previous.status satisfies 'confirmed'`, so a new member fails to compile until it is handled. | `deployments.ts` | `deployments.test.ts` "narrows to exactly three members" | High |
| INV-4 | A fragment after 0 can only insert keys. `maintenance-tx.ts` accepts `{ circuitId, verifierKey }[]` and has no variant for `VerifierKeyRemove`, `ReplaceAuthority`, a contract call, or a Zswap output, so none is constructible through this package. | `services/maintenance-tx.ts` | `maintenance-tx.test.ts` "emits one VerifierKeyInsert per circuit and nothing else", "wraps the update in an intent with no calls and no offers" | Critical |
| INV-5 | The compact-runtime `ContractState` the constructor returns and the ledger-v8 `ContractState` the transaction takes are never mixed. `contract-state.ts` is the only conversion site, and `ContractDeploy` and `MaintenanceUpdate` only ever receive the ledger one. | `services/contract-state.ts` | `contract-state.test.ts` "produces a ledger state, not the runtime one" | High |

## Runtime

Explicit checks that throw a typed error.

| INV | Statement | Enforced in | Pinned by | Severity |
|---|---|---|---|---|
| INV-6 | The fragment budget is an integer of at least one, wherever it comes from. Validated at every edge: the TOML schema, the argv parser, and `assertBudget` in `Deployer.prepare` for programmatic callers. `planFragments` trusts its input. Precedence is programmatic, then TOML, resolved once onto `PreparedState.budget`. | `config/schema.ts`, `loaders/argv.ts`, `deployer.ts` `assertBudget` | `schema.test.ts`, `argv.test.ts`, `deployer.test.ts` "rejects a budget of %s before starting the proof server" | Medium |
| INV-7 | The pruned fragment-0 state has `data`, `maintenanceAuthority` and `balance` byte-equal to the full constructor state's, and an operation set exactly equal to fragment 0's circuits. A kept name the constructor never produced, or a kept-count mismatch after pruning, is a `DeployError`. | `services/contract-state.ts` `pruneState` | `contract-state.test.ts` (7 cases, including serialized-bytes equality against a hand-pruned state); `deploy-tx.test.ts` "deploys the pruned state and returns its address" | Critical |
| INV-8 | A constructor that creates or spends a Zswap coin cannot be fragmented. The check counts `zswapLocalState.inputs` and `.outputs` on the constructor result and throws `ConfigError` before any transaction is built, because the split path assembles its intent with no Zswap offer. | `services/deploy-tx.ts` `buildPrunedDeploy` | `deploy-tx.test.ts` "refuses a constructor that creates a Zswap coin", "refuses a constructor that spends a Zswap coin" | High |
| INV-9 | A transaction the pool refuses as too large is retried with half the circuits, down to a floor of one, and only when no explicit budget was set. Refusal is recognised only by the node's `1010 … block limits` text; every other cause propagates unchanged. This applies to the deploy tx and to every insert batch, through one halving implementation. Exhausting the floor on the deploy tx is a `BlockLimitError`; on an insert it becomes a `FragmentDeployError` carrying the `BlockLimitError` as its cause, because the contract is already deployed. | `services/deploy-tx.ts` `submitClassified`, `deployer.ts` `#submitHalving` | `deploy-tx.test.ts` "raises BlockLimitError naming the fragment size", "leaves any other 1010 as a plain tx failure"; `deployer.test.ts` "halves fragment 0 on a block-limit refusal and retries" (4→2→1), "halves an insert batch on a block-limit refusal and retries" (3→1→1→1), "reports an insert refused at one circuit as a resumable failure", "does not halve when a budget was set explicitly", "leaves a non-limit failure unretried" | High |
| INV-10 | Before building fragment `i > 0` the deployer re-queries chain state and inserts exactly the circuits of that fragment still missing on chain. A fragment with nothing left is skipped without a transaction, and no update ever names a circuit already present. An empty insert list is refused outright. | `deployer.ts` `#insertRemaining` and `fragmentRemainder`, `services/maintenance-tx.ts` | `deployer.test.ts` "submits no insert when the chain already holds every circuit", "skips a fragment whose circuits already landed with an earlier insert"; `maintenance-tx.test.ts` "refuses an empty insert list" | High |
| INV-11 | After the last fragment, every artifact circuit exists on chain with byte-equal verifier keys, and no on-chain circuit lacks an artifact counterpart. A full set comparison, not a count. Any difference throws `FragmentDeployError` and leaves the record `partial`; `confirmed` is written only after this passes. The artifact's own keys are read and completeness-checked before fragment 0, so a bundle missing a key fails before any transaction. | `services/chain-state.ts` `verifyState`, `loaders/artifact.ts` `verifierKeys` | `chain-state.test.ts` (5 cases); `deployer.test.ts` "refuses to confirm when a landed key does not match the artifact"; `artifact.test.ts` "rejects a bundle with no key for a declared circuit" | Critical |
| INV-12 | Every transaction is awaited under the same `txTimeoutMs` ceiling and treated as failed on any status other than `SucceedEntirely`, through one shared wait. The caller supplies the error type: the deploy tx reports a `DeployTxFailedError` naming its record, an insert a `FragmentDeployError`. | `services/deploy-tx.ts` `awaitFinalization` | `deploy-tx.test.ts` `awaitFragmentFinalization` (4 cases), `awaitDeployFinalization` (4 cases) | High |
| INV-13 | The chain read used to compute the next fragment already shows the fragment that just landed. The deployer polls `queryContractState` until every circuit of the landed batch is present, bounded by `txTimeoutMs`, rather than planning from a state the indexer has not caught up to. | `services/chain-state.ts` `awaitCircuitsOnChain` | `chain-state.test.ts` "re-reads until the landed fragment is visible" (+2) | High |

## State transition

Chain state and the deployments ledger.

| INV | Statement | Enforced in | Pinned by | Severity |
|---|---|---|---|---|
| INV-14 | The contract address is fixed by `new ContractDeploy(prunedState)` and never changes. The address in the `partial` record, every insert update, the verify query, and `DeployResult.address` are the same value, taken from the fragment-0 result or the record and never recomputed. | `services/deploy-tx.ts`, `services/maintenance-tx.ts`, `deployer.ts` | `maintenance-tx.test.ts` "targets the address it was given"; `deployer.test.ts` "signs each insert for the recorded address at the on-chain counter and slot" | Critical |
| INV-15 | Across the run the operation set at the address only grows, and the maintenance authority does not move. No key is removed or replaced (INV-4 makes that unconstructible), and verify compares the final committee and threshold against the read taken before the first insert, throwing `ConfigError` on any difference. | `services/chain-state.ts` `verifyState` | `chain-state.test.ts` "refuses a %s that moved during the deploy" (committee, threshold, membership) | Critical |
| INV-16 | Per contract per network the head record moves only along `∅`, `confirmed`, `pending` with `--force`, or `partial` with `--force`, into `pending` (single tx) or `partial` (split, rewritten per landed fragment), and from either into `confirmed`. `partial` is never rewritten as `pending`. A promotion or progress rewrite must land on a head for the same address that is not already `confirmed`. Nothing is written before the deploy tx is submitted. | `deployments.ts` `checkRecordable`, `assertSameDeploy`, `#replaceHead` | `deployments.test.ts` (9 cases); `deployer.test.ts` "lands one deploy tx plus one insert per further fragment", "keeps a ledger-write failure inside the fragment loop as a ledger error" | High |
| INV-17 | In every written `partial` record `circuitsOnChain ∪ circuitsPending` equals the artifact's sorted circuit list, the two are disjoint, and `circuitsOnChain` is copied from the most recent chain read rather than from the plan. A chain read naming a circuit the artifact does not have is a `DeployError`. | `services/deploy-tx.ts` `toPartialRecord`, `deployer.ts` `#recordProgress` | `deploy-tx.test.ts` (6 cases); `deployer.test.ts` "records progress from the chain read, never from the plan" | Medium |
| INV-18 | The signing key and the initial private state are stored once, after fragment 0 reaches `SucceedEntirely`, from `#deployFragmentZero` alone. A resume never re-runs that write; it only stores the signing key when the private-state store has none for the address, which is what a deploy started elsewhere leaves behind. `initialPrivateState` is not recoverable on resume: it only existed inside the constructor run the original deploy did. | `services/deploy-tx.ts` `persistDeployPrivateState`, `deployer.ts` `#ensureSigningKeyStored` | `deployer.test.ts` "persists private state once on a split deploy", "does not rewrite private state on a resume", "stores the signing key on a resume when the private state has none", "leaves no record and no private state when even one circuit is too large" | High |
| INV-19 | At most one deployer transaction is unfinalized at a time, and the wallet has caught up with a transaction's dust spend before the next one is balanced. The gate records `dust.state.progress.highestRelevantWalletIndex` immediately before each submission and then waits for two things: a dust event at or past that mark has applied, and the wallet's own pending-transaction set is empty. The index alone is a global event id, so an unrelated event can carry it past the mark on a busy chain; the pending set names the transactions the wallet is still waiting on, but is empty from the start on a facade that never tracked ours. It applies to the deploy tx as well as to each insert, and is skipped after the last insert, when nothing more will be balanced. | `services/wallet-sync.ts` `readDustTip`, `dustCaughtUp` and `awaitDustSettled`, `deployer.ts` `#insertRemaining` and `#insertBatch` | `wallet-sync.test.ts` (5 cases); `deployer.test.ts` "waits for the wallet to apply the deploy spend before the first insert", "waits for the wallet to apply each insert spend before the next", "does not wait on the wallet after the last insert" | High |
| INV-20 | A deploy that fits one transaction behaves exactly as it did before fragmenting existed: the same unproven transaction, the same `pending` then `confirmed` records, the same private-state writes, no chain read, no verify, and no maintenance transaction. `DeployResult` gains only `fragments: 1` and `circuits`. The one addition it does share with the split path is the artifact key pre-flight of INV-11, which is a local filesystem read and is intended: a bundle missing a key should fail the same way whichever path it takes. | `services/deploy-tx.ts` `buildFullDeploy`, `deployer.ts` `deploy()` `single` arm | `deployer.test.ts` "leaves the single-fragment path without a chain read or an insert"; the pre-existing deploy suites, unchanged apart from the two added result fields | High |
| INV-21 | A deploy tx refused at the minimum fragment size has submitted no accepted transaction, spent no dust, written no deployments record, and persisted no private state. This covers fragment 0 only: an insert refused the same way happens after the contract exists, so the `partial` record is on disk by then. | `deployer.ts` `#deployFragmentZero` write ordering | `deployer.test.ts` "leaves no record and no private state when even one circuit is too large" | Medium |

## Privacy and disclosure

Secret handling and what leaves the process.

| INV | Statement | Enforced in | Pinned by | Severity |
|---|---|---|---|---|
| INV-22 | The maintenance signing key appears in no deployments record, no log line at any level, no `--json` output, and no error message or field. It reaches `signData` and `privateStateProvider.setSigningKey` and nothing else. | `deployments.ts` `DeploymentRecordBase`, `errors.ts` `FragmentDeployError` fields, `services/maintenance-tx.ts`, `deployer.ts` logging | `errors.test.ts` "keeps the signing key out of the message and the fields"; `deployments.test.ts` "keeps the signing key out of a partial record"; `maintenance-tx.test.ts` (2); `deploy-tx.test.ts` "carries no signing key"; `deployer.test.ts` "logs no signing-key hex on a split deploy", "… on a resume" | Critical |
| INV-23 | The split path adds no network endpoint and no runtime dependency that could open one. Every call goes through the existing providers to the configured `node`, `indexer` or `proof_server` for the selected network. `midnight-js-utils`, the one dependency added, is pure helpers. | `package.json`, the provider surface | `package.json` diff review; no module in the package opens its own connection | Medium |
| INV-24 | The identity the resume guard compares is derived from the loaded signing key and is only ever its public half. `signatureVerifyingKey` is called once, the verifying key is what gets compared and what gets logged at debug, and the derivation writes the signing key nowhere. | `services/maintenance-tx.ts` `verifyingKeyOf`, `deployer.ts` `#resumeAt` | `maintenance-tx.test.ts` "returns the public half of the signing key"; `deployer.test.ts` "logs no signing-key hex on a resume" | Critical |

## Authorization and replay

The maintenance signature, the counter, and the resume guards.

| INV | Statement | Enforced in | Pinned by | Severity |
|---|---|---|---|---|
| INV-25 | Each `MaintenanceUpdate` is signed with `signData(signingKey, update.dataToSign)` and attached at this key's own slot in the on-chain committee, read from the same chain snapshot as the counter. A committee whose threshold is not 1 is refused with `ConfigError`, because the deployer holds one key. The signature covers the address, the full insert list, and the counter. | `services/maintenance-tx.ts` `buildInsertUpdate`, `services/chain-state.ts` `signerIndex` | `maintenance-tx.test.ts` (4 cases, real crypto: verify, foreign key, tampered insert list, non-zero slot); `chain-state.test.ts` `signerIndex` (3 cases); `deployer.test.ts` "signs at this key slot when the committee is ordered differently", "refuses to insert when the committee needs more than one signature" | Critical |
| INV-26 | With a `partial` head and no `--force`, the deployer submits no `ContractDeploy`. It resumes inserts at the recorded address or throws `ConfigError`. Only `--force` starts a fresh deploy, and then the `partial` head is rotated into history first. | `deployer.ts` `deploy()` resume branch, `deployments.ts` `checkRecordable` | `deployer.test.ts` "resumes a partial head without a second deploy tx", "rotates a partial head into history and redeploys under --force", "refuses a fresh deploy over a partial head, keeping its exit code"; `deployments.test.ts` (2) | Critical |
| INV-27 | A resume proceeds only if, at the recorded address, chain state exists, the committee contains this verifying key, and every on-chain operation has an artifact circuit of the same name with byte-equal keys. Any failure is a `ConfigError` with no transaction submitted, and the record's own circuit lists are never consulted for the decision. The guard cannot tell two deploys of the same artifact with the same key apart, so a hand-edited `address` can point the run at a sibling contract. | `services/chain-state.ts` `assertResumable`, `deployer.ts` `#resumeAt` | `chain-state.test.ts` (7 cases); `deployer.test.ts` "refuses to resume against an address with no contract", "… maintained by a foreign committee", "… carrying a foreign verifier key" | Critical |
| INV-28 | The counter for each update is read from chain state immediately before that update is built. It is never cached across fragments, incremented locally, or persisted. | `deployer.ts` `#insertBatch`, `services/maintenance-tx.ts` | `deployer.test.ts` "signs each insert for the recorded address at the on-chain counter and slot"; `maintenance-tx.test.ts` "uses the counter it was given verbatim" | High |
| INV-29 | Re-running the same deploy command after any interruption once fragment 0 has landed performs only the inserts still missing on chain and ends `confirmed`, with no duplicate insert and no error for keys already present. The deploy tx is not re-awaited: chain state at the recorded address is already proof it landed, and its identifiers ride the record or are resolved once from the indexer. An insert the previous run submitted but never saw land is settled before the state the plan is built from is read. | `deployer.ts` `deploy()`, `#resumeAt`, `#settlePendingInsert` | `deployer.test.ts` "resumes a partial head without a second deploy tx", "counts inserts from the interrupted run in the fragment total", "resolves the deploy tx identifiers from chain when the record lacks them", "settles an insert the previous run left in flight before planning", "carries on when the insert left in flight never landed" | High |
| INV-30 | Between fragment 0 landing and verify passing, the deployer issues no circuit call and takes no user-interactive step. Any exit from that window other than `confirmed` is a thrown error naming the address, the landed circuits and the pending circuits, with the `partial` record on disk. That error is a `FragmentDeployError`, block-limit exhaustion included; a `ConfigError` and a `DeploymentsFileError` keep their own exit codes, because neither is fixed by re-running. `runDeploy` puts the same fields in `--json`. | `deployer.ts` `#insertRemaining` catch, `errors.ts`, `runDeploy.ts` `fragmentFields` | `deployer.test.ts` "reports a failed insert as FragmentDeployError and keeps the head partial", "records the insert txId when it never sees the tx land", "reports an insert refused at one circuit as a resumable failure"; `errors.test.ts` (2); `runDeploy.test.ts` "emits the fragmented-deploy fields as structured JSON" (+2) | High |
